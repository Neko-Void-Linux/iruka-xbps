# Iruka Package Manager

## The Name: Iruka

"Iruka" (海豚) translates to **dolphin** in Japanese. Dolphins are renowned as intelligent, agile, and highly acrobatic creatures. 

In alignment with these traits, this graphical interface was designed to be:
- **Intelligent**: Automating batch transactions, verifying package restrictions, and safely fetching database metadata asynchronously.
- **Agile**: Executing operations via clean child process lifecycles and responding instantly to package filtering and search actions.
- **Ultra-lightweight**: Built directly on C++17 and GTK 3 with minimal overhead, maintaining a flat memory footprint and fast startup times.

---

## Application Purpose

`iruka-xbps` acts as a fast desktop package manager client for Void Linux's XBPS package manager. It provides a visual platform to:
1. Search and filter local, remote, and outdated packages.
2. Browse packages by status and heuristic categories through a side panel.
3. View detailed package descriptions, properties, metadata, files and size.
4. Queue multiple install/remove actions, unmark queued packages, and apply them sequentially.
5. Execute sync, update, install and remove actions as root through a single
   privileged helper daemon launched once via Polkit (`pkexec`).
6. Manage target package repositories.

## Internationalization (i18n)

The interface is fully translatable through **gettext**. The `Options > Language`
menu offers **English**, **Español** (`es`), **Русский** (`ru`),
**日本語** (`ja`) and **Magyar** (`hu`), plus **System (default)**, which
follows the user's system locale.

English is the source language (the `msgid` strings), so it needs no catalog:
selecting it makes gettext fall back to the untranslated strings. Spanish,
Russian, Japanese and Hungarian ship as compiled `.mo` catalogs.

### Language resolution priority

1. **Saved preference** — the `ui_language` key in the user config file
   (`~/.config/iruka-xbps/iruka-xbps.conf`). This always wins when set.
2. **System locale** — `LC_ALL` / `LC_MESSAGES` / `LANG` via
   `setlocale(LC_ALL, "")`, used only when no preference is saved.

The chosen language is applied at two moments:

- **At startup** — `init_i18n()` in `src/main.cpp` reads the saved preference
  before any widget is created, so the entire UI is built in the right language.
- **At runtime** — picking a language in the menu calls `MainWindow::setLanguage()`,
  which updates the `LANGUAGE` environment variable, rebinds the text domain to
  flush gettext's internal cache, and rebuilds the UI in place (`reloadUi()`)
  without restarting the process.

### Locating the message catalogs

`utils::resolveLocaledir()` searches for the `.mo` catalogs in this order:

1. `$IRUKA_LOCALEDIR` — explicit override (staging or packaging tests).
2. `<executable dir>/po` — the Meson build tree, so running straight from
   `builddir` automatically picks up the freshly compiled catalogs.
3. `LOCALEDIR` — the install-time location (e.g. `/usr/share/locale`).

Running `./builddir/iruka-xbps` after a build therefore works out of the box,
with no environment variables required.

### Translation workflow

| File | Purpose |
|---|---|
| `po/LINGUAS` | Lists every translated language (one per line); English is the source language and is **not** listed here. |
| `po/POTFILES.in` | Source files scanned for translatable `_()` strings. |
| `po/<lang>.po` | Per-language translation catalog. |
| `po/iruka-xbps.pot` | Template generated by xgettext. |
| `src/gui/i18n.h` | Defines the `_()` / `N_()` macros and the `LOCALEDIR` fallback. |
| `src/gui/i18n_strings.cpp` | Marks strings referenced through constants (e.g. `_(IRUKA_APP_TITLE)`) so xgettext can extract them. |

To add a new language: append it to `po/LINGUAS`, create `po/<lang>.po` (via
`msginit` or `msgmerge`), translate the strings, and rebuild. The relevant
Meson/ninja targets are:

```bash
ninja -C builddir iruka-xbps-pot   # regenerate po/iruka-xbps.pot from POTFILES.in
ninja -C builddir iruka-xbps-gmo   # recompile every .mo catalog (no relink)
ninja -C builddir                  # full rebuild; .mo catalogs are compiled too
```

### Language menu internals

The `Options > Language` menu is built in `buildMenuBar()` as a group of
`GtkRadioMenuItem`s — **System (default)** (`""`), **English** (`"en"`),
**Español** (`"es"`), **Русский** (`"ru"`), **日本語** (`"ja"`) and
**Magyar** (`"hu"`) — each carrying its language code in a `"lang"` data field.
The active entry is set from the saved `ui_language` preference. English maps
to `"en"` and works without a catalog: gettext falls back to the `msgid`
strings.

Two details matter when touching this code:

- Setting the initial checked state must happen with the items' `activate`
  signals **blocked** (`g_signal_handlers_block_by_func`). Otherwise the
  `cb_menu_language` handler fires during UI construction, which re-triggers
  `setLanguage()` → `reloadUi()` → an infinite rebuild loop.
- `setLanguage()` defers the rebuild through `g_idle_add(reload_ui_cb, ...)` so
  the menu popup fully closes before its widgets are destroyed.

### Privileged helper (`iruka-helper`)

The GUI never runs as root. At startup it launches `iruka-helper` once through
`pkexec`, producing a single polkit prompt. All privileged commands (sync,
update, install, remove and repository file writes) are sent to that long-lived
helper, which executes them as root and streams their output back.

- `PrivilegedDaemon` (`core/privileged_daemon.*`) owns the pipes and sends a
  shell command per request; it reads output until the `__IRUKA_DONE__ <status>`
  sentinel and supports cancellation by sending `CANCEL`.
- The helper exits when its stdin closes (Iruka quits), and it also terminates
  via `PR_SET_PDEATHSIG` / `SIGPIPE` if the GUI dies unexpectedly, killing any
  running child in the process group.
- Both binaries must reside in the same directory: the GUI resolves the helper
  next to its own executable (`/proc/self/exe`).

### Embedded logo

The application logo is compiled directly into the binary: `logo_data.h` is
generated from `resources/icons/iruka.png` with

```bash
xxd -i -n iruka_logo_png resources/icons/iruka.png > src/gui/logo_data.h
```

`logo_pixbuf()` (in `logo.cpp`) decodes those bytes at runtime through a
`GdkPixbufLoader` and returns a new `GdkPixbuf` reference. The About dialog
uses it via `gtk_about_dialog_set_logo()`, so it works even when no icon theme
is installed. Regenerate `logo_data.h` whenever the source PNG changes.

### Key Design Patterns

- **Separation of Concerns**: Core logic runs independently of the GTK thread. The backend queries data (`xbps_command`) and parses it into records (`package`) without knowledge of UI components.
- **Asynchronous Execution & Marshalling**: Long-running operations (such as reading local package lists or formatting package details) spawn worker threads. These threads post results back to the GTK main thread using `g_idle_add`, guarded against a destroyed window.
- **Single Privilege Elevation**: Instead of invoking `pkexec` for every operation, one helper daemon is authenticated at startup and reused for all privileged commands, then torn down with the application.
- **Private Implementations**: Internal structures, enum layout markers, and GTK-specific callbacks for the main window are isolated in `main_window_private.h` to keep the public interface in `main_window.h` clean and decoupled.
